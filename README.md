# Timer Sound

Локальный динамический интервальный аудиотаймер для Android.
Kotlin + Jetpack Compose (Material 3) + Android Foreground Service.
Без сети, без бэкенда, без Room: вся конфигурация — локально (DataStore Preferences).

---

## Возможности

- **Динамический список звуковых сценариев** (неограниченное количество, добавление/удаление на лету), у каждого:
  - свой аудиофайл (MP3 / WAV / OGG через системный файловый пикер, права на чтение — persistable, файлы не копируются);
  - свой интервал `ЧЧ:ММ:СС` (пресеты 1/3/5/10/15/30 мин);
  - своя громкость 0–100 %;
  - переключатель ВКЛ/ВЫКЛ;
  - предпросмотр, замена и удаление файла.
- **Первый сценарий по умолчанию** содержит встроенный тестовый сигнал (`res/raw/beep.wav`),
  остальные сценарии пустые — файл выбирается вручную.
- **Параллельное воспроизведение**: каждый сценарий играет своим `Ringtone`
  одновременно (без последовательной очереди).
- **Имена выбранных файлов сохраняются** (§11): рядом с URI в настройках
  хранится отображаемое имя файла (`DISPLAY_NAME` от системного пикера),
  поэтому список сценариев читается даже после перезапуска — без показа голых
  путей. Если имя недоступно, показывается последний сегмент URI.
- **Глобальная авто-остановка**: без ограничения или через `ЧЧ:ММ:СС` —
  останавливает все сценарии, показывает уведомление и помечает сессию «Завершено».
- **Управление**: Старт / Пауза / Продолжить / Стоп / Сброс, чёткая машина состояний.
- **Работа с заблокированным экраном и свёрнутым приложением**:
  foreground-сервис (`mediaPlayback`), персистентное уведомление (статус,
  время до авто-остановки, ближайший звук) с кнопками **Пауза/Продолжить** и **Стоп**,
  частичный wakelock на время сессии.
- **Тайминг — по реальному времени** (`SystemClock.elapsedRealtime()`), UI ничего
  не «догоняет»: он лишь отображает состояние.
- **Настройки сохраняются** между запусками (DataStore), но **авто-возобновление
  после перезапуска приложения не предусмотрено** — после перезапуска просто
  восстанавливается конфигурация.

## Режимы сценариев

| Режим | Название | Описание |
|---|---|---|
| REPEAT | Повтор | Звук повторяется через intervalMs без ограничения. Опционально: старт по времени HH:MM (startMinutes). |
| ONCE_TIME | Время | Один звук в заданное время HH:MM. |
| INTERVAL | Интервал | Первый звук в HH:MM, далее каждый intervalMs, всего launchCount раз. |
| RANDOM | Рандом | launchCount случайных различных моментов строго внутри окна [startMinutes, endMinutes) одного дня; моменты фиксируются один раз при старт. |

## Машина состояний

```
IDLE --Старт--> RUNNING --Пауза--> PAUSED --Продолжить--> RUNNING
RUNNING/PAUSED --Стоп--> IDLE
RUNNING --авто-остановка--> COMPLETED (всё остановлено, уведомление, пометка «Завершено»)
COMPLETED --Старт/Сброс--> RUNNING/IDLE
```

## Архитектура (по ТЗ)

| Слой | Файл | Ответственность |
|---|---|---|
| UI (Compose) | `ui/App.kt`, `ui/Theme.kt`, `MainActivity.kt` | Единственный экран: статус, выбор вывода звука, авто-остановка, карточки сценариев (динамический список). Только отображает состояние и шлёт команды. |
| ViewModel | `TimerViewModel.kt` | Владелец конфигурации (DataStore), команды сервису, предпросмотр, выбор файла (`takePersistableUriPermission`). |
| Timer-session | `timer/TimerSession.kt` | Движок расписаний (REPEAT / ONCE_TIME / INTERVAL / RANDOM): планирование срабатываний по `elapsedRealtime`, пауза/резюме без «протухания» моментов, авто-остановка. UI не является источником истины. |
| SceneScheduler | `timer/SceneScheduler.kt` | Чистая математика расписаний без Android: «стенные» минуты → elapsed-шкала, моменты серии для каждого режима. |
| Foreground Service | `service/TimerSoundService.kt` | Жизненный цикл сессии, FGS + уведомление с кнопками, тик-цикл, AlarmManager.setAlarmClock, MediaSession, wakelock. |
| AudioManager | `audio/AudioEngine.kt` | По одному `Ringtone` на сценарий в потоке MEDIA (параллельное воспроизведение, громкость), предпросмотр, гарантированный `releaseAll()` на стоп. |
| Preferences | `data/PreferencesRepository.kt` | DataStore Preferences: интервалы, громкости, включённость, URI файлов, имена файлов (§11), авто-остановка. |
| Мост сервис→UI | `service/TimerStateHolder.kt` | In-process `StateFlow`: сервис пишет, UI читает. |
| Тесты | `test/.../{timer/TimerSessionTest, timer/SceneSchedulerTest, data/PreferencesRepositoryTest, model/TimerConfigTest}.kt` | Юнит-тесты машины состояний, расписаний, настроек и валидации конфига на чистой логике, с явными значениями времени. |

## Сборка и запуск

Требуется Android Studio (или JDK 17+) и Android SDK.

```bash
# из корня проекта
./gradlew assembleDebug          # или: gradle assembleDebug
```

APK: `app/build/outputs/apk/debug/app-debug.apk`.

Ключевые параметры: `compileSdk/targetSdk = 37`, `minSdk = 26`,
AGP 9.4.0 + Kotlin 2.4.20 (плагин `org.jetbrains.kotlin.plugin.compose`,
без `kotlin("android")` — встроенная поддержка Kotlin в AGP 9).

Онлайн-зависимости: только стандартные AndroidX/Compose/DataStore-артефакты,
все из `google()`/`mavenCentral()`. `INTERNET`-разрешение не запрашивается.

## Разрешения (минимальные)

- `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MEDIA_PLAYBACK` — FGS,
- `WAKE_LOCK` — точность срабатываний при погашенном экране,
- `POST_NOTIFICATIONS` — показ уведомления на Android 13+ (runtime, запрашивается при первом запуске),
- `SCHEDULE_EXACT_ALARM` — точные будильники для работы в фоне (Doze),
- `USE_EXACT_ALARM` — авто-grant от Android 13+ (нет пользовательского переключателя).

## Известные ограничения Android (задокументировано по ТЗ)
- **Doze / энергосбережение.** При длительном простое система может ограничивать
  работу приложений. Используем `AlarmManager.setAlarmClock` — единственный способ
  точной доставки будильника в Doze (особенно на EMUI/Huawei). Тик-цикл
  сервиса дублирует как страховка, но точность определяется будильником.
- **Остановка процесса системой.** Android может убить процесс при нехватке
  памяти даже с активным FGS; авто-возобновление запрещено ТЗ, поэтому сессия
  после убийства не восстанавливается.
- **Персистентные права на файл** выдаются при первом выборе (SAF,
  `takePersistableUriPermission`). Если файл удалён/отозван — сценарий просто
  не сработает (обрабатывается как сбой сценария, сессия продолжается).
- **MediaSession** (скрытая, без медиа-кнопок) обязательна для FGS типа
  `mediaPlayback` на Android 15+ — иначе система остановит сервис.

## Почему системный Ringtone, а не низкоуровневый звук (по §16)

Звуковой движок построен на системном `android.media.Ringtone`
(`RingtoneManager.getRingtone`):

- **Ноль кастомного аудио-кода.** Ringtone — системный проигрыватель Android:
  декодирование (MP3/WAV/OGG), громкость и жизненный цикл реализованы
  платформой, в приложении нет ни одного байта DSP/аудио-логики, которую нужно
  было бы поддерживать и покрывать тестами.
- **Поток MEDIA, а не «звонок».** По умолчанию Ringtone играет в потоке
  `USAGE_NOTIFICATION_RINGTONE` — это громкость звонка (часто ~1, то есть
  неслышно). Явно выставлены `USAGE_MEDIA` + `CONTENT_TYPE_MUSIC`: звук идёт на
  медиа-громкости, которую пользователь реально слышит, и совпадает с типом
  `mediaPlayback` foreground-сервиса.
- **Почему не `MediaPlayer`.** Первая версия была на `MediaPlayer`, но на
  реальном устройстве (Huawei P20 Pro, Android 10) он молча не воспроизводил
  файл — именно так выглядел исходный баг «таймер срабатывает, звука нет».
  Ringtone воспроизводит и `content://`-URI из системного пикера, а встроенный
  сигнал — как `android.resource://<package>/<raw-id>`.
- **Изоляция сценариев.** По одному `Ringtone` на сценарий — сценарии играют
  одновременно и не «съедают» друг друга; громкость задаётся на каждый плеер.
- **Гарантированная очистка.** Все плееры хранятся в `AudioEngine` и всегда
  освобождаются (`releaseAll()`): на СТОП/авто-остановке и при уничтожении
  сервиса — утечек звуковых ресурсов нет.
- **Зачем не SoundPool.** SoundPool ориентирован на короткие однотипные
  сэмплы с одним общим миксером; здесь же у каждого сценария независимый файл,
  громкость и моменты срабатывания, а сам движок полностью внутри системы.

Альтернативы вроде собственного декодера/Room-аудио сознательно отвергнуты:
дешевле и надёжнее делегировать звук платформе (§19 — без лишних зависимостей).

## Юнит-тесты

```bash
./gradlew test           # JUnit 4
```

Текущее покрытие — 41 тест: `TimerSessionTest` (21), `SceneSchedulerTest` (10),
`PreferencesRepositoryTest` (6), `TimerConfigTest` (4). Остальные слои
(Service, AudioEngine, UI) юнит-тестами не покрыты и проверяются вручную на
устройстве (см. ниже).

`TimerSession` спроектирован без Android-зависимостей (время передаётся
явным параметром `nowElapsedMs`), поэтому машина состояний и автопланирование
покрыты обычными юнит-тестами без эмулятора.

## Ручной план проверки (критерии готовности ТЗ §18)

1. **Сборка**: `gradlew assembleDebug` заканчивается успешно, APK создан.
2. **Встроенный сигнал**: сценарий 1 → «Прослушать» — слышен бип.
3. **Форматы**: на сценарии 2–5 выбрать MP3, WAV и OGG (по кнопке «Выбрать»),
   прослушать каждый.
4. **Разные интервалы/громкости**: 5 сценариев с разными интервалами и громкостями,
   ВКЛ — Старт. Через 10–30 с убедиться, что срабатывания происходят со своими
   периодами и разной громкостью.
5. **Параллельность**: выставить сценариям равные интервалы — при срабатывании звучат
   одновременно (разные треки), ни один не ставится в очередь.
6. **Авто-остановка**: установить 00:00:30 → Старт → через 30 с всё останавливается,
   уведомление «завершено», в UI статус «Завершено».
7. **Заблокированный экран**: Старт → заблокировать экран → срабатывания идут,
   уведомление отображается (Работа таймера).
8. **FGS и уведомление**: в шторке видно уведомление со статусом, временем до
   авто-остановки, ближайшим звуком и кнопками; «Пауза» останавливает отсчёт,
   «Продолжить» возобновляет с сохранённых остатков; «Стоп» — полная остановка.
9. **Состояния**: последовательность Старт→Пауза→Продолжить→Стоп→Старт работает
   корректно; после Стоп звук прекращается.
10. **Персистентность**: задать настройки → «Стоп» → перезапустить приложение —
    настройки сохранены; автоматического запуска таймера нет.
11. **Офлайн**: сборка и работа приложения не используют сеть.
12. **Режимы**: для каждого режима сценария (Повтор / Один раз / N раз / Случайно)
    задать короткое расписание и убедиться, что звук пришёл в нужный момент,
    а конечная серия завершилась сама (без «зомби»-сервиса).
13. **После завершения/Стоп**: в `dumpsys activity services com.timersound` нет
    ServiceRecord, в шторке только уведомление «Завершено» (id=1002), UI показывает
    «Завершено» / «Запустить заново».

### Проверено E2E на устройстве (Huawei COL-L29 / P20 Pro, Android 10)

- **Повтор**: 2 звука с интервалом 60 с, каждый до `MEDIA_PLAYBACK_COMPLETE`;
  Пауза → `exactAlarmCancelled`, Продолжить → возобновление с остатка; Стоп → сервис остановлен.
- **N раз**: первый в 00:12:00, интервал 00:00:20, «Сколько раз» = 3 →
  срабатывания ровно 00:12:00 / 00:12:20 / 00:12:40, три запуска плеера.
- **Один раз**: 00:49:00 — одно срабатывание.
- **Случайно**: окно 00:38–00:41, 3 звука → 00:38:00 / 00:39:00 / 00:40:00
  (все внутри окна, `count` клампится по ширине окна в минутах).
- Во всех случаях по завершении: сервис остановлен (0 ServiceRecord), в шторке
  остаётся только уведомление 1002, UI — «Завершено / Запустить заново».
