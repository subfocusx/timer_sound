# Timer Sound — план доработок

Контекст: Android/Kotlin, Compose UI, foreground-сервис `TimerSoundService` держит
`TimerSession` (машина состояний) + `SceneScheduler` (чистая математика расписания) +
`AudioEngine` (по одному `Ringtone` на канал). Конфиг — `AlarmConfig`/`TimerConfig`
(`model/TimerConfig.kt`), хранится через `PreferencesRepository` (DataStore + JSON).

Громкость канала (`volumePercent`) намеренно остаётся множителем поверх текущей
громкости медиа-потока устройства — это осознанное решение, не трогаем.

Задачи ниже независимы друг от друга и делаются по одной, с прогоном тестов после
каждой. Порядок — по приоритету (1 и 2 дают наибольший эффект при минимальном риске).

---

## 1. Переименовать режимы для понятности

**Проблема:** режим `INTERVAL` называется «N раз», но использует то же поле
`intervalMs`, что и `REPEAT` — оба слова «интервал» относятся к разным вещам,
это и путает.

**Что править:**
- `model/SceneMode.kt` — обновить `label`, чтобы название сразу говорило и про
  количество, и про интервал:
  - `REPEAT` → «Бесконечно, каждые …»
  - `INTERVAL` → «N раз, каждые …»
  - `RANDOM` → «Случайно, N раз в окне»
  - `ONCE_TIME` → «Один раз»
- `ui/AlarmCard.kt` — строка `summary` (строки ~166–181) собирает описание режима
  вручную дублируя `label`-подобную логику: свести к одному месту, чтобы текст
  на свёрнутой карточке и в `FilterChip` не расходились.

**Тесты:**
- `ui/AlarmCardFormattingTest.kt` — обновить ожидаемые строки под новые подписи.
- Ручная проверка: открыть/свернуть карточку для каждого из 4 режимов, сверить
  текст на свёрнутом виде с реальным поведением.

**Риск:** низкий, чисто текстовые изменения, логика планирования не трогается.

## 2. Предупреждение о совпадении звуков (наложение)

**Проблема:** разные каналы — независимые `Ringtone`, могут звучать одновременно.
Если два канала используют один и тот же файл и их время совпадает — получится
слышимое эхо/наложение, и пользователь не поймёт, баг это или так задумано.

**Что добавить:**
- В `model/TimerConfig.kt`, по аналогии с `missingFileAlarms()` /
  `invalidScheduleAlarms()`, добавить `overlappingAlarms(): List<Pair<AlarmConfig, AlarmConfig>>`
  (или вернуть просто множество id) — пары каналов с одинаковым `fileUri` и
  прогнозируемым временем первого срабатывания в пределах узкого окна (например,
  ≤2 сек по `SceneScheduler.fireTimesFor`/`initialRepeatFire`). Для `REPEAT` без
  фиксированного старта достаточно сравнить фазу интервалов на разумном горизонте
  (например, ближайший час).
- В `ui/App.kt` или `ui/AlarmCard.kt` показать предупреждение по той же схеме,
  что уже есть для `pastTimeWarning` / `isInvalidSchedule` (строка `isInvalidSchedule`
  в `AlarmCard.kt`) — не блокирует старт, просто предупреждает.

**Тесты:**
- Новый тест в `model/TimerConfigTest.kt`: два канала, один файл, одинаковое
  время старта → `overlappingAlarms()` находит пару; разные файлы → не находит;
  разное время → не находит.

**Риск:** низкий, чисто аддитивная фича, не меняет `TimerSession`/`AudioEngine`.

## 3. Видимый предупреждение при срабатывании лимита одновременных звуков

**Проблема:** `AudioEngine.MAX_CONCURRENT_RINGS = 10` уже защищает от перегрузки,
но при превышении лимита старые звуки глушатся молча (`Log.w`, строки 52–56
`audio/AudioEngine.kt`) — пользователь не видит, что что-то было пропущено.

**Что добавить:**
- `AudioEngine.play()` — при срабатывании лимита не просто логировать, а
  прокинуть событие наружу (например, простой `StateFlow<Int>` счётчик "сколько
  раз сработал лимит за сессию" или колбэк в `TimerSoundService`).
- `service/TimerStateHolder.kt` — добавить поле в `Ui`-снапшот, например
  `droppedRingsCount: Int`.
- В уведомлении (`buildNotification()` в `TimerSoundService.kt`) или в UI карточке
  сессии показать короткую строку, если счётчик > 0: «Часть сигналов пропущена
  (слишком много звучит одновременно)».

**Тесты:**
- Unit-тест на `AudioEngine` сложно писать без Android-мока `Ringtone` — если
  существующие тесты его не мокают, ограничиться ручной проверкой (выставить
  MAX_CONCURRENT_RINGS=2 в тестовой сборке и создать сценарий с 3+ каналами на
  одно и то же время) либо вынести счётчик глушений в чистую функцию, которую
  можно протестировать без Android SDK.

**Риск:** средний — трогается `AudioEngine` (единственный источник правды по
звуку), делать аккуратно, не меняя существующую логику `play()`/`releaseAll()`.

## 4. Глобальный предохранитель «слишком много срабатываний за сессию»

**Проблема:** `autoStopMs` останавливает сессию по времени, но не защищает от
случая, когда пользователь ошибся в `launchCount` для `INTERVAL`/`RANDOM` и
получил, например, 500 запланированных звуков подряд.

**Что добавить:**
- `model/TimerConfig.kt` — новое опциональное поле, например
  `maxTotalFiresPerSession: Int` (0 = без ограничения, как у `autoStopMs`).
- `timer/TimerSession.kt` — в `tick()` (строки 144–178) считать суммарное число
  вызовов `trigger()` за сессию, при достижении лимита — `markCompleted()` так же,
  как это уже делается для `autoStopDeadlineElapsedMs`.
- UI: поле рядом с настройкой авто-остановки (там же, где сейчас `autoStopMs`
  вводится в `App.kt`).

**Тесты:**
- `timer/TimerSessionTest.kt` — новый тест: конфиг с низким лимитом срабатываний
  и большим `launchCount` у канала → сессия переходит в `COMPLETED` раньше, чем
  доиграл бы весь `launchCount`.

**Риск:** средний, затрагивает `TimerSession.tick()` — центральный метод,
покрыт существующими тестами (`TimerSessionTest.kt`, `AllModesBehaviorTest.kt`),
прогнать оба файла целиком после изменения.

## 5. (опционально, low priority) Плавное нарастание громкости

**Идея:** при каждом срабатывании канала громкость нарастает от 0 до
`volumePercent` за 1.5–2 секунды вместо мгновенного полного звука — мягче для
слуха и меньше похоже на "дефект".

**Что добавить:**
- `audio/AudioEngine.play()` — после `ring.play()` короткий корутин-цикл,
  постепенно поднимающий `ring.setVolume()` от 0 до целевого значения.
- Сделать опциональным (настройка вкл/выкл), чтобы не ломать сценарии, где важен
  мгновенный резкий сигнал (например, таймер для тренировки).

**Тесты:** ручная проверка на устройстве — эта часть плохо тестируется юнит-тестами
(зависит от реального времени воспроизведения `Ringtone`).

**Риск:** низкий, изолированная добавка в `AudioEngine`, не трогает `TimerSession`.

## Порядок и прогон тестов

1. Пункт 1 (переименование) — безопасно первым, сразу видимый эффект.
2. Пункт 2 (предупреждение о наложении) — чистая добавка в `TimerConfig`.
3. Пункт 3 (лимит одновременных звуков — видимость) — трогает `AudioEngine`,
   делать отдельным коммитом.
4. Пункт 4 (глобальный лимит срабатываний) — трогает `TimerSession.tick()`,
   самый рискованный пункт, после него обязательно прогнать весь `test/` пакет:
   `TimerSessionTest`, `AllModesBehaviorTest`, `SceneSchedulerTest`,
   `TimerViewModelTest`, `TimerConfigTest`.
5. Пункт 5 (fade-in) — по желанию, в последнюю очередь.

После каждого пункта: `./gradlew test` (или эквивалент в вашей сборке) должен
проходить полностью, включая существующие тесты — они уже неплохо покрывают
машину состояний и планировщик, ломать их поведение нельзя.
